# ShopPilot RAG 面试讲解

更新：2026-10-06。实现事实以 [RAG 实现说明](../runtime/RAG_IMPLEMENTATION.md) 为准；旧 Dify 简历数字不用于新版 Agent。

## 一分钟介绍

我把原 Dify 的知识检索迁成受控工具，覆盖合成商品说明、政策和 FAQ。文档保留来源、版本、地区和有效期，采用 560 字符窗口、80 字符重叠；配置语义 Embedding 后，与 BM25 做混合检索，先过滤再融合排序，将引用片段交给模型规划和回答。结构化商品价格、库存、订单和兼容性由工具/规则决定，RAG 不替代这些事实源。

Agent 已有同请求内工具观察→重规划以及跨轮槽位记忆。工具最多执行六次，重复动作接管，高风险商家写操作禁止。评测区分离线哈希回归和真实模型/语义检索；我不会把规则兜底通过称为模型效果。

## 高频判断问题

**有哪些知识库？** 合成商品说明、地区政策、FAQ；订单是身份校验后的结构化工具，不是公开向量知识库。总目录为 278 商品/37 政策；这些是记录量，不等于独立知识文档数或 Chunk 数。

**RAG 的完整步骤？** 文档整理/元数据→切分→文档向量与词法索引→查询向量→硬过滤→混合召回与融合排序→引用片段组装→模型据证回答→检索与回答分别评测。接口错误有词法降级标记，不伪装成功。

**切分有哪些，为什么选当前方案？** 固定字符/Token、递归、句段、章节、语义、父子切分。当前固定字符重叠适合短且相似的政策说明，容易复现；不是语义切分，也未证明参数最优。长说明书应比较按章节/父子切分，避免表格和完整规则被切散。

**向量化和 Embedding 模型有什么区别？** 向量化是表示方法，Embedding 模型是生成语义向量的具体模型；BM25 是词法检索，不是大模型。哈希/TF-IDF 与稠密 Embedding 各有侧重，混合方案照顾中英改写和精确 SKU。

**用了哪个模型，为什么？** 用户选择阿里云百炼 `text-embedding-v4` 作为语义候选；已有账户、接口适配和中英业务需求是选择依据，不是品牌性能结论。离线测试显式用 HashingEmbedder。单条接口可用不代表全量端到端验收完成。最终与其他 Embedding 在相同语料/查询集比较 Recall、MRR、过滤、成本和延迟。

**为什么不先上 Reranker/pgvector？** 当前语料较小，内存索引和缓存足够验证链路。先证明召回与引用质量，再做神经重排消融；规模、延迟或持久化需求满足不了时再选 ANN/pgvector。不能把已有加权融合叫作神经重排。

**为什么用混合检索？** 语义向量解决同义改写，BM25 保留 SKU/术语精确匹配；地区、生效日期必须硬过滤，不能靠相似分数决定政策适用。

**如何证明好？** 离线 11 条专项样本（十条可回答、一条无证据）目前 Recall@4=1.00、MRR@4=0.875；空证据单独计分。这只是小型合成开发回归。回答忠实性、引用正确性和真实模型全量结果仍需联网运行、人工标注与校准；不声称生产成功率。

**与你原来的 Dify 有什么差别？** 原来已有 RAG 和静态工作流；升级后把知识/订单/规则工具分开，有实际 LangGraph 循环、权限边界、会话状态、引用 Trace 和版本化任务回归。两者都不等于真实商家生产接入。

## 面试诚实边界

可以说“实现了受控循环、可切换的语义检索适配器和可复现回归”；不能说“上线服务了真实商家”“Embedding 最优”“离线通过就是 LLM 通过”“已有生产 OIDC/RLS”。模型、检索、裁判和业务指标分别验证，先看是否真正执行，再看质量，再看成本/性能。
