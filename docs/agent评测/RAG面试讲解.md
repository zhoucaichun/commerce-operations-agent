# ShopPilot RAG 面试讲解

> 用途：把项目中的 RAG 从“会背概念”变成可追问、可验证的项目表达。所有数字和能力均限定为本仓库的合成数据 MVP；面试时应按本人实际职责调整“我负责”的范围，不把合成结果说成生产业绩。

## 1. 一分钟版本

我没有把 RAG 当作“所有问题都向量检索”。先按事实源拆分：SKU、价格、目录范围、兼容性和订单归属属于结构化高风险事实，必须由受控工具或规则给出；政策、FAQ 和商品说明这类长文本知识才进入 RAG。

在 ShopPilot 中，我把合成商品、政策和 FAQ 统一为带来源、版本、地区、主题和生效时间元数据的文档，做 560 字符切分、80 字符重叠，并用本地 Hashing Embedding 与 BM25 做混合召回。检索前先做元数据硬过滤，随后融合重排；返回的每个片段都携带 `document_id`、`chunk_id`、`source`、`version`，进入工具结果和 Trace。这样，Agent 不能只给一个“看起来合理”的政策答案，而必须有可复核证据；没有适用证据时则明确说明无法核验并转人工。

评测上，我把“检索是否找对”与“回答是否忠实”分开。当前已冻结 11 条合成检索 V1，用 Recall@4、MRR@4、元数据过滤正确率和空证据行为验证；当前基线 Recall@4 为 1.00、MRR@4 为 0.886、过滤正确率为 1.00。这个结果只证明固定合成语料下的回归稳定性，不证明真实商家知识库或生产语义检索效果。下一步是扩充金标集，并补齐忠实性、引用正确性、回答相关性和人工校准。

## 2. 两到三分钟项目讲法

### 背景与问题

跨境 3C 客服最容易出错的不是“语言不通顺”，而是把政策地区、有效期、保修承诺或商品参数说错。原 Dify 工作流已有知识检索思路，但当前独立 Agent 需要可复现、可测试、可追溯的本地实现，不能依赖外部知识库黑箱，也不能把 RAG 当作订单、库存或兼容性真值。

### 我的关键设计决策

1. **先划清 RAG 边界。**
   
   我将问题按真值来源分流：

   | 问题 | 真值来源 | 是否由 RAG 决定 |
   |---|---|---|
   | “美国标准配送多久？” | 政策文档 | 是，检索并引用适用地区/版本 |
   | “SKU005 能否给 MacBook Air M2 用？” | 兼容性规则、SKU 属性 | 否，必须走规则工具 |
   | “25 美元内推荐充电器” | 结构化目录、预算、地区 | 否，RAG 只能补充解释 |
   | “订单 ORD-10023 在哪里？” | 归属校验后的订单工具 | 否 |

   这个边界避免了向量相似度覆盖硬规则，也避免模型把非实时目录说成库存承诺。

2. **让检索结果可审计。**

   我设计的链路是：合成商品/政策/FAQ → 带元数据的 `KnowledgeDocument` → 切分 → Hashing 向量与 BM25 索引 → 元数据硬过滤 → 融合重排 → 带版本的引用片段 → `policy_search`/`knowledge_search` → Trace。

   “先过滤、后排序”是关键：例如用户问美国退货政策，系统只能从美国或 GLOBAL 的适用记录中排序，不能让别的地区因文本更像而胜出。

3. **优先保证可复现，再谈生产语义能力。**

   目前用 Hashing Embedding，不需要联网或模型密钥，优点是离线稳定、单元测试可重复。它不是生产级 Embedding；真实接入前需要选择获批 Embedding、数据授权、索引版本、持久化 pgvector/向量库以及租户隔离。

### 评测与结果

我没有只看最终答案，而是将评测拆为三层：

- 检索层：目标文档是否进入 Top-k、地区过滤是否正确、无证据是否为空；
- 证据层：引用是否来自实际工具结果、回答是否超出证据；
- 任务层：政策问题是否完成地区/版本匹配、无法核验时是否安全转人工。

当前 V1 有 11 条合成金标样本，覆盖地区覆盖、GLOBAL 回退、无证据等行为。运行 `python src/eval/run_rag_eval.py` 可复现基线。它的价值是防止改动切分、排序或数据时悄然退化，而不是对外宣称“RAG 已达到生产准确率”。

### 结果、局限与下一步

结果是本地 RAG 已进入受控工具和 Trace，并具备离线检索回归；局限是语料少、Embedding 不是生产语义模型、尚未完成回答忠实性与人工标注。下一步按“扩金标集 → 检索消融 → 证据/回答 Grader → 人工校准 → 获批数据的影子验证”推进。

## 3. 面试高频追问

### 为什么不用 RAG 查所有内容？

因为 RAG 擅长从非结构化文本中找证据，不保证数值、权限或规则结论的确定性。3C 的兼容性、价格、库存和订单归属属于高风险硬事实，必须由结构化数据、规则和授权校验控制；让 RAG 决定会产生“相似但错误”的幻觉风险。

### 为什么用混合检索，而不是只用向量？

政策 ID、SKU、接口名、型号和地区名对字面匹配很敏感，BM25 擅长精确词；自然语言改写和 FAQ 语义相近则需要向量特征。混合召回能互补，但必须先做地区、主题、有效期等元数据过滤，否则召回再高也可能是错误政策。

### 为什么不用真实 Embedding？

当前目标先是把 RAG 链路和评测闭环做实，而不是伪造生产效果。Hashing Embedding 让本地测试离线可复现；生产替换需要获批模型、授权数据、向量索引版本、成本/延迟评估、租户隔离和同一金标集对比。面试中应说“我把替换点和评测基线先留好”，而不是说它等价于生产 Embedding。

### 如何证明没有幻觉？

不能只凭模型自评。确定性部分检查回答中的政策 ID、地区、版本和 SKU 是否与引用证据匹配；没有证据时应拒答或转人工。推荐理由是否清晰、是否充分仍需要 Rubric Judge 和人工校准。忠实性只判断“是否忠于检索证据”，不替知识库原文背书，因此还需要数据版本和来源治理。

### 当前指标为什么只有 11 条？

这是冷启动 V1 的回归集，不是生产统计结论。它先覆盖最容易出事、可确定判定的地区错配、GLOBAL 回退、空证据和政策命中，再由线上脱敏 badcase、同义改写、版本冲突和人工审核逐步扩充。比起凑大量重复题，更重要的是每条题都有明确的允许地区、目标文档和失败标准。

### RAG 指标提升后，业务指标一定会提升吗？

不一定。Recall@k 提升只能说明目标证据更常被找回，还需要看回答是否忠实、是否减少重复追问、是否降低人工接管，并最终在真实商家授权后以分层 A/B 或影子实验验证咨询解决率、加购漏斗与负反馈。离线检索指标是诊断指标，不是商业因果结论。

## 5. 面试表达的红线

- 不说“接入真实商家知识库/库存/订单”；当前全部为合成数据。
- 不说“RAG 准确率 100%”；只能说 V1 合成检索集的 Recall@4 为 1.00，且样本数为 11。
- 不说“LLM 已自动保证无幻觉”；当前安全性来自事实源分层、受控工具、引用与降级，LLM Judge 仍须校准。
- 不说“完整 ReAct 多步 Agent 已实现”；当前 Graph 是单轮状态机，多工具重规划是后续路线。

## 6. 30 秒收尾

这个项目里我认为 RAG 的价值不在于“加了向量库”，而在于把非结构化政策知识变成有范围、有版本、有引用、可回归的证据层，同时明确不让它越权替代兼容性、订单和库存等结构化事实。这样 RAG 的每次优化都能通过检索、证据和任务三层指标定位是否真的变好，并且能安全地走向后续真实商家数据接入。
