# 近年 Agent 评测论文与工程框架综述

> 检索范围：2023–2026。优先纳入 ICLR、NeurIPS、ACL 等主会代表作；同时保留与客户支持、RAG、生产反馈直接相关的 Industry/区域会议论文。后者不应被误写为 CCF-A，但对 ShopPilot 的工程价值可能更高。CCF 分级以发布时最新目录为准。

## 1. 结论先行

没有任何单一公开 Benchmark 可以证明 ShopPilot 适合跨境 3C 商家。通用 Benchmark 只能帮助拆解能力；真正的发布证据必须在本项目的商品、兼容性规则、政策、订单授权和租户边界上产生。

最适合 ShopPilot 的组合是：

```text
AgentBench：分层分析 Agent 决策能力
ToolBench / BFCL：工具选择、调用与参数契约
τ-bench：多轮客服 + 工具 + 政策 + 最终状态
JourneyBench：SOP 路径遵守
RAGAS / ARES：检索相关性、忠实度、答案相关性
人工校准：验证 LLM Judge 不能替代的业务判断
```

## 4. 火热方法：应采用什么，而不是跟风什么

### 4.1 Trace-first evaluation

先追踪模型调用、工具、Guardrail、Handoff，再将 Trace 用结构化 Grader 打分。适合发现“最终答案似乎正确，但工具/权限路径错误”的问题；是 ShopPilot 的首要方法。

### 4.2 Environment-state / task-state evaluation

不要只比文本。将每个 Case 配套合成目录、订单、政策和工单状态，判断最终状态是否正确。这是 τ-bench、JourneyBench 类客服评测最值得迁入的思想。

### 4.3 Contract evaluation

对工具的名称、JSON 参数、授权、返回 Schema、重试和幂等做确定性检查。它应覆盖所有可验证事实，是最便宜、最稳定的 Grader。

### 4.4 LLM-as-a-Judge + 人工校准

仅评估语义质量，例如“推荐理由是否针对预算和用途”“澄清是否必要”。采用盲评、成对比较或清晰通过/失败 Rubric；检查位置偏差、长度偏差、自我偏好和跨模型偏差。评测分数必须和独立人工校准集比较，不能把 Judge 输出当真值。

### 4.5 评测驱动数据飞轮

把确认的线上失败、人工改写、低置信度和高频追问脱敏后进入候选池；领域 Owner 审核、编写预期和 Grader 后，才进入回归集。不是每月替换旧题，而是持续累积不可退化的安全/事故案例。

### 4.6 可靠性与扰动测试

对同一任务进行同义改写、信息缺失、工具超时、工具返回空值、前序上下文冲突等扰动。用户面向的系统首先看单次成功与多次一致性；`pass@k` 只可描述能力上限，不能作为发布依据。

### 4.7 Agent-as-a-Judge：暂不作为核心

可让评测 Agent 查询证据、检查轨迹并生成审核报告，但它会引入新的工具、提示注入、成本和不可重复性问题。ShopPilot 先实现确定性 Grader + 校准 LLM Judge；当基础评测稳定、且人工审核成本成为瓶颈时，再试验受限权限的评测 Agent。

## 5. 工程框架地图与建议

| 工具/框架 | 强项 | 局限 | 对 ShopPilot 的建议 |
|---|---|---|---|
| 本仓库 `src/eval` + JSON 报告 | 数据、规则、CI 和安全边界完全可控 | 需要自行建设可视化与实验比较 | **当前唯一必选**；先做 Eval V1。 |
| [LangSmith](https://docs.langchain.com/langsmith/evaluation-types) | LangGraph 生态、数据集、离线/在线评测、代码/LLM/成对评测 | 托管依赖与数据治理评估 | 未来若接受托管，可作为开发诊断加速器。 |
| [Langfuse](https://langfuse.com/docs/evaluation/overview) | Trace、数据集、实验、线上评分闭环；可自托管 | 仍需自行保证评测契约和数据脱敏 | 生产可观测性候选，优先评估自托管。 |
| [Arize Phoenix](https://arize.com/docs/phoenix/) | 开源、OpenTelemetry/OpenInference、Trace 与实验诊断 | 不替代领域 Grader | 可作为开放可观测性候选。 |
| [Ragas](https://docs.ragas.io/en/latest/concepts/metrics/available_metrics/) | RAG 与 Agent 指标，包括 Faithfulness、Tool Call Accuracy、Agent Goal Accuracy | 很多指标仍依赖 LLM Judge，且不理解你的业务权限 | 当前 V1 已借鉴其分层指标思想；后续评估是否引入部分库，不能作为唯一发布门禁。 |

共同原则：框架负责收集、比较、展示和触发实验；ShopPilot 自己的 Case 契约、证据快照、权限规则和发布门槛才是不可外包的核心资产。

## 6. 推荐阅读顺序与项目行动

1. **τ-bench + JourneyBench**：先理解“客服成功不只看最终回答，还要看政策路径与最终状态”。
2. **ToolBench / MetaTool / BFCL**：定义受控工具和 Trace Grader。
3. **AgentBench + MINT**：补齐多轮规划、状态保持与失败诊断。
4. **ARES / RAGAS**：在当前 RAG V1 的召回/过滤基础上，补齐证据忠实度和回答相关性。
5. **Agent-in-the-Loop**：Merchant Console 有真实人工使用后建设反馈数据飞轮。

对应本项目的近期工程优先级不是接入更多平台，而是完成 `ShopPilot Eval V1`：统一 Case Schema、冻结回归集、确定性 Grader、Trace 报告和人工校准流程。之后再比较 Qwen、Gemini 或其他模型，才有可解释的模型选择结论。
